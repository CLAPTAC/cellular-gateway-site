How it works

One path from API to mobile network

Your software never talks to a phone directly. The gateway authenticates the request, chooses a healthy device, and pushes the command over a persistent WebSocket. The phone sends the SMS or places the call and reports the result back.

  • Phones connect out to the server, so they can sit behind NAT or on mobile data.
  • Commands queue while no phone is online and are dispatched when one reconnects.
  • Inbound SMS and every status change can be pushed to your system as webhooks.
Capabilities

Everything between your API and the carrier

Start with a reliable device link, then grow into group routing, webhooks and role-based access.

SMS in and out

Send up to 1600 characters per request and store every inbound message. Multipart splitting is handled by the phone.

Voice calls

Start and end outbound calls through the phone's dialer and follow each call from DIALING to ENDED.

Group routing and failover

Pool phones into groups, pick by health, battery or load, queue while offline, and retry failed SMS on another device.

Signed webhooks

HMAC-SHA256 signatures, five delivery attempts with backoff, and a delivery history for every endpoint.

Secure by default

Production mode refuses weak secrets, sessions use httpOnly cookies, and webhooks cannot reach private networks.

QR provisioning

Create a device in the dashboard and scan once on the phone. No long tokens to type.

Operator dashboard

Online status, battery, messages, calls, commands, analytics, webhooks, users and API keys in one portal.

Roles and API keys

Admin, operator and viewer roles for people, and revocable API keys for your services.

Runs on one small server

FastAPI, PostgreSQL and Next.js in Docker Compose, with automatic HTTPS through Caddy or your own reverse proxy.

Integrate

Plain HTTP, any language

There is no SDK to install. Create an API key in the dashboard and call the endpoints from your backend. Results arrive as webhooks, or you can poll.

API reference   Webhooks

curl
curl -X POST https://gateway.example.com/api/v1/messages \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"group": "primary", "to": "+15551234567", "message": "Hello"}'
Python
import os, requests

r = requests.post(
    "https://gateway.example.com/api/v1/messages",
    headers={"X-API-Key": os.environ["GATEWAY_API_KEY"]},
    json={"group": "primary", "to": "+15551234567", "message": "Hello"},
    timeout=15,
)
r.raise_for_status()
print(r.json()["status"])
Node
const res = await fetch("https://gateway.example.com/api/v1/messages", {
  method: "POST",
  headers: {
    "X-API-Key": process.env.GATEWAY_API_KEY,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ group: "primary", to: "+15551234567", message: "Hello" }),
});
if (!res.ok) throw new Error(await res.text());
console.log((await res.json()).status);
Deploy

Choose how you run it

Both options use Docker Compose and PostgreSQL. Release builds of the Android app require HTTPS.

Dedicated host

Caddy is bundled, obtains certificates automatically and is the only service that publishes ports (80 and 443).

bash
docker compose --env-file .env.production \
  -f docker-compose.prod.yml up -d --build
Production guide

Behind your existing proxy

Already running nginx, Apache, Traefik or Caddy? The shared-host file binds to loopback so your proxy stays in charge of TLS.

bash
docker compose --env-file .env.production \
  -f docker-compose.shared.yml up -d --build
