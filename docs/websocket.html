Devices

WebSocket protocol

The device channel: authentication, message types, command acknowledgements, heartbeats and close codes.

Phones keep one WebSocket open to the server. The server pushes commands, and the phone reports acknowledgements, heartbeats, inbound SMS and call state. Every message is a JSON object with a type.

Connect#

  1. Register. The phone calls POST /api/v1/devices/register with its key and token.
  2. Open the socket at wss://<host>/ws/devices.
  3. Authenticate. The server replies with ready, or closes with an error code.
Handshake headers
GET /ws/devices
X-Device-Key: dev_...
X-Device-Token: dvt_...

Headers keep credentials out of proxy and access logs. The query form /ws/devices?device_key=...&device_token=... is still accepted for simple clients (the bundled simulator uses it), but avoid it in production. A new connection for the same device replaces the old one.

Server to phone#

ready
{ "type": "ready", "connection_id": "...", "device_id": "...", "timestamp": "2026-01-01T12:00:00+00:00" }
command
{
  "type": "command",
  "command": {
    "type": "SMS_SEND",
    "request_id": "req_123",
    "device_id": "...",
    "payload": { "to": "+15551234567", "message": "Hello" }
  }
}

Command types in the schema: SMS_SEND, SMS_CANCEL, CALL_START, CALL_END, DEVICE_STATUS, DEVICE_COMMAND, PING. The Android app executes SMS_SEND, CALL_START, CALL_END, PING and DEVICE_STATUS, and answers anything else with a FAILED acknowledgement.

Other server messages: heartbeat_ack, command_ack_received (with request_id and status), sms_received_ack (with message_id), call_state_ack (with call_id and status), pong, and error (with message) for unknown message types.

Phone to server#

heartbeat
{
  "type": "heartbeat",
  "payload": {
    "battery": 87,
    "signal_strength": 78,
    "network": "4G",
    "manufacturer": "Google",
    "model": "Pixel",
    "android_version": "14",
    "app_version": "0.3.0"
  }
}

battery and signal_strength are integers from 0 to 100. The Android app sends a heartbeat every 10 seconds.

command_ack
{
  "type": "command_ack",
  "payload": {
    "request_id": "req_123",
    "status": "COMPLETED",
    "result": { "sent": true, "to": "+15551234567", "parts": 1 },
    "error_message": null
  }
}

Typical statuses: ACKNOWLEDGED first, then COMPLETED or FAILED (CANCELLED is also valid). On failure include error_message.

sms_received
{ "type": "sms_received", "payload": { "from": "+15551234567", "body": "Hello", "to": null, "received_at": null } }

to, received_at and metadata are optional.

call_state
{ "type": "call_state", "payload": { "state": "ACTIVE", "number": "+15551234567", "request_id": "req_456", "call_id": "..." } }

Reported states include DIALING, RINGING, ACTIVE, IDLE and ENDED. The server maps them to call statuses.

ping
{ "type": "ping" }

The server answers with {"type": "pong"}. Separately, the Android client sends WebSocket protocol pings every 20 seconds.

Close codes#

CodeMeaning
4401Unauthorized: unknown device or wrong token
4403Device disabled
4404Device not found
4000Replaced by a newer connection from the same device
4429Too many failed attempts from this IP
1011Server error

Presence and offline detection#

A device is ONLINE while its socket is open. If a device has no live socket and its last heartbeat is older than DEVICE_HEARTBEAT_TIMEOUT_SECONDS (default 45), a background check marks it OFFLINE. Queued commands are dispatched when it reconnects.
