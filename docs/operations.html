Operations and limits

Logs, health checks, migrations, backups, troubleshooting, and the current limitations of the gateway.

Day-to-day#

TaskHow
Health checkGET /health returns {"status":"ok","service":"Cellular Gateway"}
Logsdocker compose -f docker-compose.prod.yml logs -f server. Failures in the background workers (offline detection, command queue, webhook delivery) are logged
MigrationsApplied automatically on container start. Create one with alembic revision --autogenerate -m "description" in server/
Backupdocker compose ... exec postgres pg_dump -U gateway cellular_gateway > backup.sql
Upgradegit pull, then docker compose ... up -d --build. Plan a short interruption; phones reconnect automatically

Troubleshooting#

SymptomLikely cause
Server exits at startup with "Refusing to start with insecure configuration"Production safety checks. The message lists each setting to fix
409 No online devices availableThe target phone is offline and neither queue nor group was used
Device flips between ONLINE and OFFLINEA proxy timeout under about 30 seconds, battery optimization killing the app, or an unstable mobile connection
Phone cannot connect from a release buildThe server URL must be https:// with a valid certificate
Dashboard shows login errors after a domain changeNEXT_PUBLIC_API_URL is baked in at build time; rebuild the dashboard image. Also check CORS_ORIGINS
429 on loginToo many failed attempts; wait for the window (default 5 minutes) or adjust LOGIN_RATE_LIMIT_*
Webhook creation returns 400The URL is not https (in production) or resolves to a private address
Webhooks stop arrivingCheck the endpoint's delivery history. After 5 failed attempts a delivery is marked FAILED

Known limitations#

  • Single server instance. Device sockets and background workers are in-process. Running more than one replica is unsupported and would need shared state such as Redis.
  • Real-phone validation. SMS and call behaviour has been tested with the simulator and automated tests, not yet on physical phones with SIM cards.
  • Placeholder signal data. The Android app currently reports a fixed signal strength and network type in its heartbeat, so those two fields in the dashboard are not real measurements. Battery level is real, and routing uses battery, not signal.
  • No carrier delivery receipts. SENT means the phone accepted the message, not that the recipient received it.
  • No idempotency keys on message or call creation. Deduplicate retries on your side.
  • Not yet available: scheduled messages, message templates, USSD and SIM management.
  • API keys inherit the permissions of the administrator who created them and apply only to the messages, calls and commands endpoints.
  • The rate limiter keeps its state in memory, so it resets when the server restarts.
  • The dashboard has no automated tests. The server has a pytest suite.
